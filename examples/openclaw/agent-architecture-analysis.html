Architecture Report

OpenClaw 项目分析

OpenClaw 是一个本地优先的多渠道 AI Gateway 与 agent runtime。它把消息入口、会话路由、模型调用、工具执行、插件能力、记忆检索、后台任务和多端协议放到同一个控制平面里，而不是只做一个 LLM chat wrapper。

核心结论

Agent 类型 本地 Gateway 编排的工具型、长任务型、插件扩展型个人 agent。
控制面 Gateway 负责 WebSocket RPC、鉴权、会话、路由、任务状态和事件。
执行面 嵌入式 Pi runner、ACP harness、子 agent、模型 provider 和工具系统。
一句话架构判断： 项目最难的部分不是“怎么调模型”，而是如何在多渠道、多 provider、多插件、多会话和长任务并发下，保持热路径懒加载、会话一致、权限可控、上下文可审计。

从源码看，OpenClaw 的核心路径是：外部渠道或客户端把请求交给 Gateway；Gateway 解析会话、校验权限、返回 accepted run；后台任务进入 agentCommand；再进入嵌入式 Pi runner；runner 编译系统提示词、历史、附件、工具 schema 和 memory 结果，驱动模型和工具循环，最后把 transcript、事件、trajectory 和投递状态落回 Gateway 的会话控制面。

系统边界

Gateway 是长期驻留进程，也是系统边界。它接收 WebSocket 协议帧、渠道消息、CLI/移动端/桌面端请求，维护节点 presence、会话 store、任务状态和插件 runtime。Agent runner 不直接拥有外部世界；它通过 Gateway 和工具层访问渠道、文件、网络、媒体和插件能力。

Channel turn path

Channel 插件进入统一 turn kernel：ingest、classify、preflight、resolveTurn、record inbound session、dispatch reply、finalize。这个设计让 Discord、Telegram、Slack 等渠道能共享会话记录和 reply pipeline，同时保留各渠道 adapter 的差异。

并发模型

runEmbeddedPiAgent 先派生 session lane，再派生 global lane。session lane 序列化同一会话写入，global lane 控制更宽的运行队列。cron lane 有 nested lane 以避免死锁。

上下文与记忆

OpenClaw 的上下文不是单一 prompt，而是由 workspace bootstrap 文件、system prompt config、session transcript、skills snapshot、tool schemas、附件、runtime metadata、memory/RAG 结果共同组成。系统提示词由 buildAgentSystemPrompt 每次重建，并把稳定前缀和动态上下文分开，便于缓存。

多 Agent 协作

多 agent 不是简单的函数调用，而是 session 和 task 层面的拓扑：父会话通过 sessions_spawn 创建 subagent 或 ACP session；子任务拥有自己的 sessionKey、transcript 和生命周期；完成后通过 internal event 或 message 回到父会话。插件 runtime 也可以拿到 subagent runtime surface。

可观测性

项目有明确的 trajectory flight recorder：运行开始记录 session.started 和 trace.metadata，上下文提交前记录 context.compiled，prompt 提交记录 prompt.submitted，结束记录 model.completed、trace.artifacts、session.ended。这让一次 agent turn 可以从 prompt、工具、usage、compaction、fallback 和 transcript 多维度复盘。

这套可观测性对 agent 系统很关键：LLM 错误往往不是单点 bug，而是上下文、工具、模型、权限、记忆、渠道投递共同造成的系统行为。trajectory 把这些因素压成可导出的证据包。

设计判断

做得强的地方

  • Gateway 和 runner 分层清楚：控制面负责协议、会话和任务，执行面负责模型/工具循环。
  • sessionKey 是系统主轴：路由、delivery、memory 可见性、subagent、transcript 都围绕它组织。
  • 插件是 ownership boundary：manifest 提供静态元数据，runtime surface 提供受信能力，工具层有契约校验。
  • 长任务有工程化处理：accepted ack、agent.wait、runId、dedupe、queue lanes、timeout、fallback、trajectory。
  • 上下文设计考虑成本和可缓存性：稳定系统 prompt 前缀、动态 heartbeat、tool search compact、memory bounded result。

复杂度集中点

  • 热路径不能随意 broad load plugin/provider/channel registry；项目已有大量 AGENTS 规则在约束这个方向。
  • 会话生命周期和 delivery context 很容易产生跨渠道错误，需要严格依赖 prepared runtime facts 和 last route。
  • 插件是 in-process trusted native runtime，不是强沙箱；安全边界主要靠配置、权限、approval 和契约校验。
  • memory 有多后端、多语料、多 visibility 规则；检索质量、延迟和 fallback 都需要 live proof 才能断言。

面试式解释

可以把 OpenClaw 解释成“Slack/Telegram/Discord/本地客户端共享的 agent OS”。Gateway 类似内核控制面，session store 是进程表和文件系统索引，plugin manifest 是设备树，runner 是执行调度器，tools 是系统调用，memory/RAG 是可查询的长期状态。它的工程重点是把 LLM 的不确定性包在确定性的协议、队列、权限、会话和审计结构里。

待验证点
