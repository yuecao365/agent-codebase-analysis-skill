Architecture Report

OpenClaw Project Analysis

OpenClaw is a local-first multi-channel AI Gateway and agent runtime. It is not just an LLM chat wrapper: it combines messaging entry points, session routing, model execution, tool execution, plugin capabilities, memory retrieval, background tasks, and a typed multi-client protocol into one control plane.

Core Thesis

Agent Type A local Gateway-orchestrated personal agent for tools, long-running work, and plugins.
Control Plane The Gateway owns WebSocket RPC, auth, sessions, routing, task state, and events.
Execution Plane Embedded Pi runner, ACP harnesses, subagents, model providers, and tools do the work.
Architecture judgment: The hard part of OpenClaw is not calling a model. The hard part is keeping multi-channel, multi-provider, multi-plugin, multi-session, long-running agent work lazy, auditable, permissioned, and recoverable.

The main path is: a client or channel sends a request to the Gateway; the Gateway validates permissions, resolves the session, and accepts a run; a background task enters agentCommand; the embedded Pi runner compiles system prompt, history, attachments, tool schemas, and memory results; the model/tool loop runs; then transcript, events, trajectory, and delivery state are written back through the Gateway control plane.

System Boundary

The Gateway is the long-lived system boundary. It accepts WebSocket protocol frames, channel messages, CLI/mobile/desktop requests, and node presence. The agent runner does not own the outside world directly; it reaches channels, files, web, media, and plugin capabilities through Gateway-mediated tools and runtime surfaces.

Request Lifecycle

The Gateway agent handler validates params, caller scope, model override authority, attachments, channel hints, and idempotency. It returns an accepted run first, dispatches the real work in the background, and supports a final response with the same response id. Clients can also wait through agent.wait.

Channel Turn Path

Channel plugins enter a shared turn kernel: ingest, classify, preflight, resolveTurn, record inbound session, dispatch reply, and finalize. This lets Discord, Telegram, Slack, and other channels share session recording and reply mechanics while retaining channel-specific adapters.

Agent Runner

The runner has two layers. agentCommand resolves model, provider, session, workspace, trajectory, and fallback. runEmbeddedPiAgent handles session/global lane queueing, attempts, timeout/abort, compaction, fallback, event bridging, and final result assembly.

Concurrency Model

runEmbeddedPiAgent derives a session lane and a global lane. The session lane serializes writes for one conversation; the global lane limits broader runtime work. Cron gets a nested lane to avoid deadlocks.

src/agents/pi-embedded-runner/lanes.ts:3 src/agents/pi-embedded-runner/lanes.ts:8 src/agents/pi-embedded-runner/run.ts:380

Failure Recovery

The execution layer distinguishes aborts, run timeouts, idle timeouts, tool execution timeouts, compaction timeouts, and provider/model fallback. Trajectory records model.completed and trace.artifacts for later inspection.

Context And Memory

OpenClaw context is not a single prompt string. It is assembled from workspace bootstrap files, system prompt config, session transcript, skill snapshots, tool schemas, attachments, runtime metadata, and memory/RAG results. buildAgentSystemPrompt rebuilds the system prompt per run and separates stable prefix content from dynamic context for caching.

Memory/RAG Design

memory_search declares itself as a mandatory recall step before answering questions about prior work, decisions, dates, people, preferences, or todos. The memory-core plugin can search memory files, session transcripts, and wiki supplements. The QMD backend uses agent-scoped XDG state and can fall back to the built-in index when unavailable or when it fails.

Multi-Agent Design

OpenClaw's multi-agent model is session and task based. A parent session can use sessions_spawn to create a subagent or ACP session. Child tasks get their own sessionKey, transcript, and lifecycle, then report back through internal events or messages. Plugin runtime surfaces can also receive subagent capabilities.

Observability

OpenClaw has a trajectory flight recorder. A run records session.started and trace.metadata, records context.compiled before prompt submission, records prompt.submitted, and finishes with model.completed, trace.artifacts, and session.ended. This gives enough evidence to inspect prompt, tools, usage, compaction, fallback, and transcript state after a turn.

src/agents/pi-embedded-runner/run/attempt.ts:2014 src/agents/pi-embedded-runner/run/attempt.ts:2026 src/agents/pi-embedded-runner/run/attempt.ts:3263 src/agents/pi-embedded-runner/run/attempt.ts:3477 src/agents/pi-embedded-runner/run/attempt.ts:3966 docs/tools/trajectory.md

This matters because agent failures are rarely isolated model mistakes. They usually involve context, tools, model capabilities, permissions, memory, and delivery behavior. Trajectory turns those moving parts into an auditable bundle.

Design Judgment

Strengths

  • The Gateway/runner split is clear: control plane for protocol, sessions, and tasks; execution plane for model and tool loops.
  • sessionKey is the system spine: routing, delivery, memory visibility, subagents, and transcripts all attach to it.
  • Plugins are ownership boundaries: manifests provide static metadata, runtime surfaces provide trusted capabilities, and tool loading validates contracts.
  • Long-running work has real infrastructure: accepted ack, agent.wait, runId, dedupe, queue lanes, timeout, fallback, and trajectory.
  • Context engineering accounts for cost and caching: stable prompt prefix, dynamic heartbeat, compact tool search, and bounded memory results.

Complexity Hotspots

  • Hot paths must avoid broad plugin/provider/channel registry loading; the repo has many local rules enforcing this direction.
  • Session lifecycle and delivery context are easy places for cross-channel bugs, so prepared runtime facts and last-route state are critical.
  • Native plugins are trusted in-process code, not a hard sandbox; safety depends on config, permission policy, approvals, and contract validation.
  • Memory spans multiple backends, corpora, and visibility rules; retrieval quality and fallback behavior need live proof.

Interview-Ready Explanation

A useful way to explain OpenClaw is: it is an agent operating system for Slack, Telegram, Discord, local clients, and plugins. The Gateway is the kernel-like control plane, the session store is the process table plus transcript index, plugin manifests are the capability registry, the runner is the scheduler/executor, tools are system calls, and memory/RAG is searchable long-term state. The engineering goal is to wrap LLM uncertainty in deterministic protocol, queues, permissions, sessions, and audit trails.
